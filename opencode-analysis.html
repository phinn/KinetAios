核心评价

OpenCode 是目前架构最先进的开源 AI 编程 Agent。它用 Effect 框架把"会话持久化 → 上下文组装 → 模型调用 → 工具执行 → 事件流投影"做成了完整的 Function Pipeline，还自己造了 opentui（终端 UI 框架）和 httpapi-codegen（SDK 代码生成器）。但先进也意味着复杂——Effect beta、17 个 patch、668 个文件的 opencode 核心包，对贡献者门槛极高。

核心优势 ✅

🏗️ 架构与工程

1

Effect 框架贯穿全局

3116 处 yield*、306 处 Effect.gen。Session/LLM/Tool 全部以 Effect generator 组织，天然支持并发取消、资源管理、错误通道分离、可观测性。不是"用了一点 Effect"，而是"整个项目 Effect-first"。

2

V2 Session Core — 持久化优先设计

Session 不是内存对象，而是 SQLite 持久化的 "durable inbox"。Prompt 先写入 session_input 行，再通过 SessionExecution.wake() 调度。支持 crash recovery、多 prompt 排队、Context Epoch 缓存基线管理。这是比 Claude Code 更先进的 session 架构。

3

Context Source 注册表系统

System Context 不是硬编码 system prompt，而是可注册的 ContextSource 生产者。每个 Source 有独立的 key、JSON codec、loader、baseline/update renderer。支持中途变更并产生 Mid-Conversation System Message。这是声明式上下文管理的最佳实践。

4

SDK Contract IR 自动生成

packages/httpapi-codegen 把 HttpApi 定义编译成 SDK Contract IR，再发射出 Effect client 和 Promise client 两套 SDK。生成的 types.gen.ts 有 13,622 行。不需要手写 SDK，API 变了重新生成即可。

5

自研 opentui TUI 框架

不依赖 blessed/ink，自己用 React-like 的 SolidJS 信号系统做了终端渲染器（@opentui/core + @opentui/solid），支持组件化、虚拟滚动、keymap。TUI 包 204 个文件、31K 行，是完整的终端应用。

🧠 能力与生态

1

全协议 LLM Provider 支持

3 套协议适配器（Anthropic Messages、OpenAI Chat/Responses、Bedrock Converse、Gemini），12+ Provider（含 Copilot、OpenRouter、xAI）。Provider 切换只改配置不改代码。Provider 测试有 recorded cassette 回放机制。

2

14 种 Provider-Specific Prompt 模板

不同模型有不同的 prompt 文件（anthropic.txt、gemini.txt、gpt.txt、codex.txt、kimi.txt、copilot-gpt-5.txt…），每种模型用最适合的指令格式。还有 plan-mode.txt 等模式切换模板。

3

多形态部署：CLI / TUI / Desktop / Web / Embedded

同一个 core，渲染层可以是终端（tui）、桌面（Electron）、Web（SolidStart SSR）。还有 Embedded OpenCode 模式——在进程内通过内存 HttpClient 复用 Server 路由。

4

codemode — 沙箱代码执行

Effect 原生的沙箱 JS 解释器，可以在受限环境中执行 schema 描述的工具代码。runtime.ts 有 3465 行，是一个完整的 AST 解释器。用于安全地执行模型生成的代码。

5

21 种语言 README + 18 种 i18n

README 翻译了 21 种语言（含中文简繁、日语、阿拉伯语、孟加拉语…），术语表（glossary）也有 16 种语言。国际化做到了极致。

🔧

丰富的工具系统

read/write/edit/grep/glob/shell/task/webfetch/websearch/plan/todo/lsp/apply_patch/skill/mcp，每个工具有 .ts 实现和 .txt 模型描述文件。支持 truncate 大输出到临时文件。

🧪

704 个测试文件

包含 provider recorded cassette（回放真实 API 响应）、session runner 集成测试、compaction 测试。Provider 测试支持 cache.recorded 模式。

🤖

双 Agent 模式

build（全权限）和 plan（只读分析）。还有 @general 子 Agent 用于复杂搜索和多步任务。plan Agent 默认拒绝文件编辑，执行 bash 前要权限。

🔌

MCP + Plugin 双扩展

支持 MCP 协议（含 OAuth），还有自有的 Plugin SDK（v1 Promise 风格 + v2 Effect 风格）。Plugin 可以注册自定义工具、命令、Provider、Skill。

📋

完整的 Compaction 策略

当上下文窗口溢出时，有 summary.ts 做摘要压缩。支持 overflow.ts 检测窗口边界，revert.ts 支持回退到压缩前状态。这是生产级的长会话管理。

📈

爆发式增长

从 2025-06-29 的 5.8 万总下载到 2026-01-29 的 1019 万。日均增长 30 万+。GitHub Star 和 npm 趋势极陡。这是真实的产品吸引力。

CONS
核心问题 ❌

⚠️ 架构债务

1

Effect 4.0 beta 依赖 — 全线未稳定

effect@4.0.0-beta.83、@effect/platform-node@4.0.0-beta.83、@effect/opentelemetry@4.0.0-beta.83 全是 beta。而且需要 patch（patches/effect@4.0.0-beta.83.patch）。一旦 Effect 4.0 正式发布 breaking change，整个项目要改 300+ 处 Effect.gen。

2

17 个 Patch — 依赖维护噩梦

patch 了 solid-js、ai-sdk（google/xai/mistral/openai-compatible）、modelcontextprotocol/sdk、effect、tanstack/virtual-core 等。每个 patch 都是"上游不修就得永远维护"。Bun 的 patchedDependencies 机制虽好，但 patch 文件积累到 17 个已经是技术债信号。

3

opencode 包膨胀 — 668 文件 / 176K 行

核心的 packages/opencode 有 668 个 TS 文件。单包包含 session、tool、provider、config、server、lsp、mcp、git、snapshot、worktree… 等几十个子模块。虽然内部有 src/ 目录分层，但没有进一步拆成独立包。对比 packages/core 已经拆出来了，opencode 本身还是太重。

4

V1 / V2 双轨并存

packages/core/src/ 下有 v1/ 目录，packages/plugin/src/ 下有 v1/ 和 v2/ 两套。opencode/src/session/ 有 V1 和 V2 的桥接代码（event-v2-bridge.ts、message-v2.ts）。迁移没完成，维护两套 API 的成本很高。

🚨 实践风险

5

Effect 学习曲线极高

Effect 的 generator 函数、Layer 依赖注入、Stream、Schema、TaggedError 对绝大多数前端/Node 开发者是全新的。AGENTS.md 用大量篇幅解释 Effect 编码规范（"不要嵌套 yield*"、"Effect 中同步逻辑不要返回 Effect"），本身就说明需要严格的规范来约束开发者。

6

Bun 独占 — 非 Node 兼容

packageManager: bun@1.3.14。大量使用 Bun.file()、bun test、Bun 特有 API。放弃 Node.js 生态意味着：CI 必须用 Bun、开发者必须安装 Bun、某些 Node-only 的库不兼容。虽然 Bun 性能更好，但这是一个排他性选择。

7

CONTEXT.md 过度工程化

CONTEXT.md 有 32,094 字，定义了 30+ 个专有名词（Context Epoch、Safe Provider-Turn Boundary、Admitted Prompt、Prompt Promotion、Session Drain…）。这种概念密度对贡献者极不友好。一个人能维护这套词汇表，但社区贡献者很难上手。

8

SST + Cloudflare 强绑定

部署层用了 SST (sst.config.ts) + Cloudflare Workers。infra/ 目录有 lake.ts、enterprise.ts、monitoring.ts 等。这意味着 OpenCode 的后端服务（share、auth、console）绑定了特定云厂商。自托管需要绕过这些基础设施。

⚡ 潜在风险点

typescript 7.0-native-preview — 用了 @typescript/native-preview（Go 重写的 tsc），还是 dev tag。正式版行为可能不同。
node-pty patch — @lydell/node-pty 1.2.0-beta.12 + postinstall fix-node-pty。终端模拟依赖不稳定。
opentui 自研风险 — 不用 blessed/ink 是创新，但 TUI 框架只有这一个用户。如果团队放弃维护，迁移成本无限大。
anomalyco 组织 — 从 sst-community/anomaly 看似是 SST 团队孵化。商业化路径（enterprise 包）可能影响开源方向。

INSIGHTS
对 KinetAios 的启示

✅ 可以借鉴

Context Source 注册表 — KinetAios 目前 system prompt 是硬编码的。可以学习 OpenCode 的 ContextSource 模式，让 memory block、project context、agent config 等成为独立的注册式 context producer，支持动态更新和 Mid-Conversation System Message。

📌 值得关注

Session Durable Inbox — prompt 先持久化再执行的设计很优雅。KinetAios 目前的 session model 可以参考：把 prompt 作为 durable input 写入 SQLite，再通过 wake/schedule 执行。这样 crash 后可以恢复未完成的 prompt。

⚠️ 不要照搬

Effect 全家桶 — OpenCode 用 Effect 是因为团队（SST/anomaly）本身就是 Effect 生态核心贡献者。KinetAios 用纯 TypeScript 更合适：对贡献者友好、调试简单、不需要理解 Effect 的 Layer/Stream/Schema 概念。Effect 的类型体操（yield* 类型推断）在 IDE 中也有性能问题。

💡 差异化机会

NEXUS 可视化 — OpenCode 没有会话关系可视化（只有列表）。KinetAios 的 NEXUS 轨道视图是独特优势。
多引擎实时切换 — OpenCode 切 Provider 改配置，KinetAios 的 Direct/Claude Code/Codex 三引擎热切是更强。
长期记忆 — OpenCode 有 snapshot 但不是语义检索。KinetAios 的 FTS5 + embedding recall 是差异化。

🚨 需要警惕

过度抽象的代价 — OpenCode 的 CONTEXT.md 有 32K 字定义 30+ 概念。KinetAios 要保持简单：一个概念能用一句话解释就不要发明术语。
patch 堆积 — OpenCode 有 17 个 patch。KinetAios 应该尽量用原生依赖，patch 是最后的手段。
