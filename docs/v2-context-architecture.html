2execHistory 生命周期

execHistory 是 V2 引擎的核心上下文载体 —— 它在 Planner → Executor → Replan 之间传递,承载着所有步骤的执行历史。理解它的流转就理解了整个 V2 引擎。

L1: Reactive Trim

位置: AgentLoop.ts:88

保留: 尾部消息 + _memory + _pinned

预算: trimBudget 30K (hifi 60K)

L2: interStepCompact

位置: V2Engine:1063

每个步骤完成后,对 execHistory 调 LLM 做摘要压缩。

fingerprint: msgs.length + lastContent[:200]

预算: interStepCompactBudget 20K (hifi 40K)

L3: finalizeContext

位置: V2Engine:1088

整个 run 结束时,把 execHistory 压缩后写入 conv.directHistory。

用途: 跨 turn 的会话记忆(下一轮 user input 时注入)。

预算: interStepCompactBudget 20K

6Crash Recovery 恢复流程

7上下文管理 Bug 修复记录

P0 重试失败历史污染 execHistory
步骤 3 次重试全失败时,失败的完整 ReAct 历史(大量 tool_calls + 错误结果)被永久追加进 execHistory。 后续重试和步骤面临巨大的失败上下文噪声(3 次重试 = 3 倍失败历史累积),且步骤间压缩无法完全消除。
stepStartLen 记录步骤开始时的 execHistory 长度。只有 stepDone=true 时才用 stepMessages.slice(stepStartLen) 追加增量。失败时重试仍能看到 step.result 通过 retryNote 传入。
P0 interStepCompact fingerprint 碰撞
去重 fingerprint 仅使用 messages.length 和 lastContent.length 做 hash,碰撞率极高。 不同内容只要长度相同就误判「没变」,跳过必要的上下文压缩。
直接用 content 前 200 字符的文本做 fingerprint:${"${msgs.length}:${lastContent"}.slice(0, 200)}。不用 hash 函数,省 CPU 且无碰撞。
P0 失败步骤摘要消息误导后续步骤
步骤失败时(3 次重试耗尽),摘要消息写死 「📋 步骤[X] 完成」。后续步骤看到「完成」会误以为前步成功, 依赖一个实际失败的步骤的产出。主流程和 replan 路径都有此问题。
摘要消息区分成功/失败。成功 → ✅ 完成,失败 → ❌ 失败 并显示失败原因。
P1 crash recovery trim 可能丢弃步骤摘要
恢复路径执行 trimHistoryToTokenBudget 按尾部截断时,可能砍掉前置的步骤完成摘要消息(📋), 导致模型丢失前置进度记忆,可能重复执行已完成步骤。
已知约束,暂不修复。STEP_EXECUTOR_PROMPT 已注入已完成步骤列表(status + result),影响可控。未来可给 📋 消息加 _pinned 标记。
