# 四引擎实测：同一个 Excel 交叉分析任务，Claude Code / Codex / 自研引擎差距有多大

> 上篇结尾挖的坑，这篇来填。同一个真实数据分析任务，四套 Agent 引擎各跑一遍，把差距摊开讲清楚。数据都是真的，账本贴在文内。

上一篇《我开源了一个 Claude Code 的本地化替代品：856 个 commit 踩过的坑》结尾预告了这篇。写完那篇我又提交了 5 个 commit，现在是 861 个。

## 测试场景：不是玩具 demo

先交代任务背景，因为这决定了结论的适用范围。

场景：医疗器械 CRM 的停机/装机数据交叉分析。多个 xlsx、单表几十万行，要做多表交叉对账（按医院、按机型、按时间窗聚合），最后产出一份暗色主题的 ECharts 交互报告。真实业务数据，我自己每周都跑的活。

这个场景对 Agent 引擎的考验很刁钻：

- **大文件**：xlsx 直接塞上下文等于自杀，必须流式解析
- **多轮工具链**：读表 → 筛选 → 交叉 → 聚合 → 出报告，一环断全断
- **上下文爆炸风险**：任何一个环节把原始数据吐进对话，下一轮 API 调用就上天

四个选手：

| 选手 | 架构 | 备注 |
|---|---|---|
| **V1 Direct** | 自研 ReAct 循环 + 25+ 插件工具 | KinetAios 内置 |
| **V2 Direct** | Plan·Execute·Verify·Judge 四层 | 同为自研 |
| **Claude Code** | `claude -p --output-format stream-json` | 大厂原版 CLI |
| **Codex** | `codex exec --json` | Open系 CLI |

## 结果先行

| 结论 | 引擎 | 一句话理由 |
|---|---|---|
| ✅ 首选 | **V1 Direct** | 插件工具全链路 + 上下文三级兜底，token 最低 |
| ⚠️ 可用 | **Claude Code** | 自带上下文管理优秀，但没有插件工具，每步绕路 |
| ❌ 不推荐 | **V2 Direct** | 同样的活，token 翻 2-3 倍 |
| ❌ 不推荐 | **Codex** | 沙箱限制 + 无插件工具，分析效率最低 |

意外吗？我自己的 V2 输得比 Claude Code 还惨。下面讲为什么。

## 发现一：决定胜负的不是模型，是工具链

四家背后跑的其实都是能力不错的大模型。真正的分水岭在**模型能不能直接摸到数据**。

V1 有 `excel_read`（SAX 流式解析，不爆内存）+ `csv_filter`（服务端筛选排序）+ `csv_analyze`（列类型推断+统计摘要）。整条链路里，**模型从头到尾没见过一行原始数据，只见过筛选后的结论**。

Claude Code 和 Codex 呢？没有这些工具。它们只能 Bash 调 python 绕路——每解析一个 xlsx，就是一次"把文件内容往上下文里塞"的豪赌。塞小了分析不动，塞大了直接撞窗口。

> 数据分析场景里，"模型看不到原始数据"不是缺陷，是特性。

这是做 Agent 半年来最反直觉的认知之一：**给 agent 的上下文要像给新同事的交接文档——只给必要的，其余他应该自己查。**

## 发现二：token 账本——钱花在哪了

我对自己的使用数据做了次全量审计（12 个会话、341 turns、227 次 API 调用），几个数字值得所有做 Agent 的人看看：

**总量：131 万 tokens，费用 $0.30。**（GLM 便宜，这也是敢放开跑的前提）

**但分布极度畸形：**

```
<2K     110 次   84K tokens   ( 6.4%)
2-5K     48 次  157K tokens   (12.0%)
5-10K    33 次  240K tokens   (18.3%)
10-20K   30 次  432K tokens   (33.0%)  ← 最大消耗区间
20-50K    4 次  107K tokens   ( 8.2%)
50-100K   1 次   99K tokens   ( 7.6%)
>100K     1 次  190K tokens   (14.5%)  ← 单次灾难
```

**7.5% 的调用吃掉了 63% 的预算。** 那 19 万 token 的单次灾难是怎么回事？拆开看：

一个 turn 里执行了 174 个工具步骤，其中 16 次 `read_file`，平均每个返回 15K 字符——全部累积在消息历史里。ReAct 循环的代价模型就在这：第 N 步调用时，前 N-1 步的工具结果**每一轮都重新发送一遍**。累积发送量是 N²/2 级别的重复内容。

这就是为什么 V2 输得最惨：Plan JSON + Verify 回顾 + Judge，同样的任务**三次 LLM 调用**起步，而数据分析场景里多数 Verify 是自我感动——数据算对就是对的，让模型"回顾一下"不会让它更对，只会让账单更厚。

> Plan/Verify/Judge 的价值在代码任务，不在数据分析。没有免费的严谨，每一次"再检查一遍"都是真金白银。

## 发现三：崩不崩，取决于上下文兜底

数据爆炸那一刻，四家表现完全不同：

- **V1**：三级 fallback——全预算重试 → 砍半 → 1/4 激进裁剪，配合 `compactHistory` 把早期对话压成结构化摘要。优雅降级，任务不中断
- **V2**：有 fallback，但 Plan JSON 不参与压缩——救得了工具结果，救不了自己的计划
- **Claude Code / Codex**：各自的内部上下文管理。黑盒，平时很稳，炸的时候你什么都做不了

顺便修过一个小而致命的 bug：早期版本三级 fallback 的第二级裁完忘了重试，直接 return 退出——任务在"还能救"的地方静默死亡。这类 bug 的恶心之处在于它不报错，只是"跑了很久然后没下文"。

## 发现四：记忆——动态检索 vs 一次性快照

V1/V2 每轮可以 `recall_memory` 实时检索历史（"上次装机报告的格式是什么来着"——当场查）。

CLI 引擎只有快照注入：`--append-system-prompt` 或 prompt 前置，开局塞一次，会话中途发生的一切它都不知道。

短任务无感，长任务（正是数据分析的常态）差距会滚雪球。

## 意料之外的结论

**1. V1 赢这个场景，不代表 V1 全面赢。** 写代码时我会切回 Claude Code——它自带的上下文管理、原生 git 集成至今仍是第一梯队。引擎选型本质是**任务-引擎匹配问题**，不存在全能冠军。这也是 KinetAios 做成"多引擎同窗、随时切换"的原因：不是炫技，是因为真的需要。

**2. Codex 的 skill 系统其实最完善。** `$skill-name` 语法、SKILL.md frontmatter、repo/user/system/admin 四级作用域、隐式调用检测、依赖声明——设计上比另外三家讲究。可惜插件生态不互通，`excel_read` 这些工具它一个都用不上。**生态 > 设计，又一次。**

**3. harness 的权重被系统性低估。** 同一个模型，换个引擎跑，成本差 3 倍、成败互异。大家都在卷模型跑分，但对你账单影响更大的，是你脚下的这层 harness。
