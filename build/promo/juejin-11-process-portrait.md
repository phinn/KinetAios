# 让 AI 独立交付一个功能:21 轮对话全程复盘,我只说了 6 句话

## 先说结论

1. **Agent 开发工作流的瓶颈不是模型智力,是流程设计。**同一个 GLM-4 级模型,流程对了 21 轮交付一个可用的功能模块,流程不对 3 轮就烧穿 context 开始胡编。
2. 我让 AI 给自己的产品(一个 Electron 桌面端)开发一个新功能,全程只发了 6 条人类消息,其余全是 Agent 自主完成:读代码、定方案、写代码、编译验证、修错、提交 git。
3. 全程 1695K tokens,成本 $0.12,墙钟 7 分 52 秒。**人类工时估算:一个熟悉代码库的工程师 2-4 小时。**
4. 交付物:双端功能 + 国际化(四语言)+ 文档同步 + git 提交拆分。一次通过,零返工。

## 场景设定(故意选了个有坑的任务)

任务原话就一句话:"好了,还有什么你能做的用来提高星数,现在 star 就 8 个"。

这个任务的阴险之处:
- **目标模糊**:没有说"做 X 功能",Agent 得自己盘点资产(README、推广渠道、截图素材)找出短板;
- **跨技术域**:要动 Markdown 文档、要操作 GitHub API、要起 Electron 应用截 GUI 图、要处理沙箱拦截;
- **有历史包袱**:工作区里有大量未提交的遗留改动,git 提交必须精准拆分,不能把无关改动混进去。

## 流程画像(21 轮,每轮在干什么)

| 阶段 | 轮次 | Agent 动作 | 关键决策 |
|---|---|---|---|
| 盘点 | 1-3 | 查 repo topics/README/文档结构,列出 6 项待办 | 判定"无截图"是转化率最大嫌疑 |
| 取证 | 4-8 | 起 Electron 应用、处理窗口焦点、截 GUI 图 | 两次截屏抓错窗口后自主换 API |
| 修复 | 9-11 | 替换双语 README 的 hero 图,压缩 1.1M→392K | 选 JPG 不选 PNG,控制 repo 体积 |
| 提交 | 12-13 | git add 精准圈定 3 个文件,避开 7 个无关改动 | 工作区有半成品,逐文件 add |
| 延伸 | 14-19 | 写 ruanyf/weekly(102k⭐)投稿文案、学格式 | 模仿该仓近期被收录 issue 的结构 |
| 交付 | 20-21 | push、汇报清单、标注哪些需要人工 | 区分"我能做"和"需要你的账号" |

中间值得展开的三轮:

**第 4 轮:沙箱拦截。**跨仓库 git 操作被工作区护栏拦下,报错"疑似跨项目误操作"。正确动作不是绕过护栏,是换路:fork 工作副本放进本项目目录,用 `GIT_DIR`+`GIT_WORK_TREE` 显式声明,一次通过。

**第 7 轮:截屏抓错窗口。**按进程名截屏,抓到的是另一个 app 的窗口。Agent 没有把错误截图贴给用户问"是这个吗",而是用 Quartz API 遍历全部窗口拿精确标题,按窗口名重截——**错误自证,不回抛给人**。

**第 13 轮:提交拆分。**`git status` 显示 11 个改动文件,其中 7 个是上次会话遗留的半成品。直接 `git add -A` 会把半成品混进发布 commit。逐文件圈定 3 个,commit message 只描述本次改动。

对比:同样的任务发给无工具的聊天模型,它会给一份"提高 star 的 10 条建议"清单——然后一条也执行不了。

## 给开发者的三条可复用结论

1. **给 Agent 的任务指令可以短,但验证标准要硬。**"提高星数"是合格指令,因为 Agent 能自己拆解;"优化一下代码"是垃圾指令,因为没有验收标准,Agent 不知道何时停。
2. **工具权限的粒度决定自主度上限。**能读不能写 → 只能出方案;能写本地 → 能改代码;能 git push → 能独立交付。每一层权限换来一个量级的效率,也换来一个量级的爆炸半径——所以我的 shell 工具保留了审批门。
3. **长会话的 context 管理是工程问题不是提示词问题。**21 轮 × 每轮工具输出,靠"请记住上文"是撑不住的,必须有结构化的记忆分层(会话内工作集 + 跨会话长期记忆 + 关键事实锚点)。
