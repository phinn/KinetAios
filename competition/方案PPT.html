Problem

现有 AI Agent 的瓶颈

🧠
单 Agent 上下文有限
复杂任务需要拆解→并行→汇总，单 Agent 在一个上下文窗口里全做容易跑偏、遗漏

Security

四层安全防护

🤖 第 1 层：Agent 层 — dispatch_agent 隔离
子 Agent 只读工具 · 不能 write/edit/shell/递归 dispatch · 独立上下文 · 完成即销毁
sandbox 第 2 层：沙箱 — 三级权限
readOnly（只读 cwd 内文件）· workspaceWrite（只写 cwd）· fullAccess（不限）· 远程 MCP Agent 强制 workspaceWrite
🌐 第 3 层：网络层 — SSRF 防护
拦截内网 IP · 拦截云元数据端点（169.254.169.254）· DNS rebinding 防护 · 错误信息脱敏
📄 第 4 层：文件层 — 快照回滚
每次 write / edit 前自动存入 .kinet-snapshots/ · 一键回滚 · Agent 破坏不了文件系统
Shell 确认桥：shell 执行前弹窗确认 · approval=never 可跳过 · MCP 远程调用也走确认
Error Handling

异常分支与优雅降级

子 Agent 执行失败 ├── 工具超时 → 5min 超时保护 → 返回错误摘要给主 Agent ├── LLM 调用失败 → Provider SSE 断流 → 自动重试 ├── 子 Agent 结果不完整 → 主 Agent 判断: │ ├── 补充说明后重新 dispatch_agent │ ├── 主 Agent 亲自执行（降级为单 Agent） │ └── 标记失败 → 在最终回复中说明 └── 主 Agent 上下文溢出 → 自动压缩历史 → 继续执行
容错设计：子 Agent 失败不阻断主流程。主 Agent 可重试、降级、或跳过。
超时保护：每个工具调用和子 Agent 都有独立超时，不会无限等待。

dispatch_agent 工作机制

// 主 Agent ReAct 循环中调用 dispatch_agent({ prompt: "审查 src/ 目录的安全漏洞，关注 SQL 注入和 XSS", engine: "claudeCode" // 可选：跨引擎借力 }) // 内部执行流程： 1. 创建独立 history（不污染主 Agent 上下文） 2. 加载 readOnlyTools()：7 个只读工具 3. 调用 runAgentLoop()（Direct）或 CLI one-shot（CC/Codex） 4. 子 Agent ReAct 循环（maxTurns ≤ 8） 5. 子 Agent 完成后 文本汇报 → 注入主 Agent 上下文

Appendix

答辩 Q&A

Q: KinetAios 和 AgentTeams / AutoGen 等多 Agent 框架有什么区别？
AgentTeams/AutoGen 是企业级多容器编排平台，需要 Docker/K8s。KinetAios 是单进程桌面应用，通过内置 dispatch_agent 在一个进程内实现多 Agent 协同——主 Agent 拆解任务，子 Agent 独立上下文并行探索，零基础设施。
Q: dispatch_agent 的子 Agent 为什么是只读的？
安全设计。子 Agent 有独立上下文，如果允许写文件和 shell，主 Agent 就无法有效审计。只读 + 完成后文本汇报，确保子 Agent 不会破坏系统，也不会无限递归。
Q: 三个引擎有什么实际区别？为什么要多引擎？
Direct 是自研 ReAct（唯一用内置工具的引擎），Claude Code 和 Codex 是 CLI 封装。多引擎的价值：① 不同模型擅长不同任务，按需切换；② dispatch_agent 可跨引擎调度，主 Agent 用 Direct 做编排，子 Agent 用 Claude Code 做深度分析；③ 不被单一供应商锁定。
Q: 说"自研引擎"，到底自研了什么？
ReAct 推理循环（Thought→Action→Observation）、上下文管理（溢出砍半+LLM压缩+孤立清理）、12个Node.js工具、dispatch_agent子Agent调度、SQLite+FTS5记忆提取与召回、三级沙箱安全、文件快照回滚。这些全部自研，不是调用某个Agent框架。
