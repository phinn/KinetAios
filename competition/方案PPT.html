Problem

企业设备运维数据分析的痛点

📂
数据散落
设备停机率数据散落在多个 Excel/CSV 文件中，格式不统一，跨表关联困难
⏱️
人工耗时
经销商交叉分析需要跨表关联，人工处理耗时长，出错率高
📊
缺乏工具
异常检测需要统计建模，业务人员缺乏工具，依赖稀缺的数据工程师
🔄
无法规模化
分析报告需要可视化+定期更新，但分析能力无法规模化复制
核心矛盾：数据复杂度在增长，但分析能力无法规模化。
Current Approaches

现有方案的不足

方案问题
传统 BI 报表 固定模板，无法应对临时分析需求。每次新需求都要走开发排期
单 Agent 数据分析 上下文有限，复杂任务容易跑偏。一个 Agent 既要清洗又要分析又要出图，容易顾此失彼
标准 AgentTeams Worker 只有 LLM 调用能力，无法操作文件 / 执行代码 / 处理 Excel
纯代码脚本 每次需求变更都要改代码，不够灵活，无法理解自然语言指令
我们需要：多 Agent 协同调度 编排 + 每个 Agent 有真正的工具执行力 执行

数据工程师 KinetAios MCP "你擅长数据清洗和预处理" 输出标准格式 CSV，处理缺失值

Appendix

答辩 Q&A

Q: 为什么不直接用标准 Worker？
标准 Worker 无法操作文件系统、执行代码或处理 Excel。真实数据分析场景中，Worker 需要读 CSV、跑 Pandas、生成图表 — 这些都需要本地工具能力，而 KinetAios 正好提供了。
Q: KinetAios 和 AgentTeams 是什么关系？
上下游。AgentTeams 是编排层（Manager），KinetAios 是执行层（增强 Worker）。两者通过标准 MCP 协议对接，互不侵入。
Q: 如果不用 KinetAios，能用别的替代吗？
可以。KinetAios MCP Server 遵循标准 MCP JSON-RPC，任何 MCP 客户端都能调用。但 KinetAios 的优势是开箱即用 — 12 工具 + 18 插件 + ReAct 循环 + 记忆系统，不用组装。
Q: PolarDB-PG 换成别的数据库可以吗？
可以。数据层通过 MCP 协议抽象，只需更换 MCP Server 实现，Agent 逻辑不受影响。PolarDB-PG 是推荐项，不是硬依赖。
