9 定位差异：谁解决什么问题

🔵 KinetAios — 「Agent 仪表盘」

核心价值: 一个桌面应用同时跑五个引擎, 统一 UI, 统一记忆, 统一工具链。

不跟谁竞争: 不跟 Claude Code 拼单引擎智能度; 不跟 Codex 拼沙箱安全; 不跟 WorkBuddy 拉普通用户。

真正的对手: 没有。多引擎热切 + Memory Blocks + NEXUS 可视化 + 飞书/企微集成的组合, 目前市场上没有同类产品。最接近的是 Cursor 的 Composer, 但那是 IDE 内的, 不是独立 Agent 仪表盘。

适合: 想同时用 Claude + GPT + 国产模型的开发者; 需要长期记忆跨会话的场景; 嵌入式/工业领域的开发者 (23 个专用插件); 需要通过飞书/企微远程控制 Agent 的场景。

🟠 Claude Code — 「最强单引擎 CLI」

核心价值: Claude 模型直驱 + 极致工具质量 + MCP 生态 + 社区网络效应。

适合: Claude 重度用户; 习惯终端工作流的开发者; 需要稳定可靠的 coding agent 的团队。

天花板: 只能用 Claude 模型。无长期记忆。闭源不可定制。

🟢 Codex CLI — 「最安全的 Agent」

核心价值: Rust 原生性能 + OS 级沙箱 + OpenAI 模型 + 开源社区 (105K star)。

适合: 安全敏感的代码场景; OpenAI 重度用户; 需要审计 Agent 行为的合规场景。

天花板: 只能用 OpenAI 模型。无长期记忆。TUI 交互受限。

🟣 OpenCode — 「架构最先进」

核心价值: Effect 函数式架构 + Event Sourcing + Context Source 注册表 + 自研 TUI。

适合: 架构研究者; 想学习"正确"做 Agent 的人; 需要 crash-proof 的场景。

天花板: Effect beta 依赖是定时炸弹; 666K 行代码贡献门槛极高; 实际用户少。

🟢 WorkBuddy — 「职场人 AI 工作台」

核心价值: 非技术人员用自然语言完成办公任务 + 腾讯生态 + Skill 市场。

适合: HR / 运营 / 产品经理; 需要做 PPT/报告/数据分析的白领; 企微/QQ 用户。

天花板: 不做编程; 数据在云端; 闭源无定制能力。

10 对 KinetAios 的战略建议

竞品启示与行动项

1. 保持多引擎差异化 (独占优势, 不需要学竞品)

KinetAios 是唯一能在同一 UI 里热切 Direct/DirectV2/DirectV3/Claude Code/Codex 的产品。Claude Code 和 Codex 都是单引擎锁定。OpenCode 虽然 multi-provider 但 agent loop 只有一个。这是核心壁垒, 继续加固。

2. 学 Codex: 补沙箱短板 (高优先级)

当前 KinetAios 安全靠 confirm 弹窗, 是五个产品中最弱的。Codex 用 bwrap/seatbelt 做了 OS 级隔离。建议: Windows 上至少做 AppContainer 或 Job Object 级别的进程限制, 限制 Agent fork 出的子进程的文件系统/网络访问范围。不需要做到 Codex 那么重, 但要比 confirm 弹窗强。

3. 学 Claude Code: 补工具质量 (中优先级)

Claude Code 的 6 件套 (Bash/Edit/Write/Read/Glob/Grep) 每个都打磨得极好。KinetAios 的 grep 和 glob 是自己实现的, 功能可以但边界 case 处理不如 Claude Code 细。建议逐个工具做"边缘 case 清单"测试。

4. 学 OpenCode: 部分借鉴 Context 设计 (低优先级, 选择性搬)

不要搬: Context Source 注册表 (320 行类型体操, KinetAios 的 string[] 拼接够用); Durable Inbox (admit→promote 两阶段, 单进程不需要); Event Sourcing (一个 turn 存 JSON blob 的简单模型更好)。

可以借: Context Epoch 的 baseline + snapshot 概念 — 把 Memory Blocks 的状态 hash 化, 只有变化时重新注入, 减少 token 消耗。steer/queue 的概念 — 未来支持"中途打断 LLM 重新指方向"时可以参考。

5. 学 WorkBuddy: 补非技术用户路径 (探索性)

WorkBuddy 的"自然语言 → 任务拆解 → 执行 → 交付 PPT/报告"的模式, 面向 10x 更大的用户群体。KinetAios 的 office-suite 插件已经有雏形。如果要做 To B / To 普通用户, 可以在 DirectV3 自适应流水线上叠一层"办公场景路由", 根据意图自动选插件。

6. 不需要学的: Effect 全家桶 / Rust 重写

OpenCode 的 Effect 4.0-beta 是维护噩梦。Codex 的 Rust 重写对 KinetAios 没有参考价值 (KinetAios 是 Electron 应用, 不是 CLI)。TypeScript + better-sqlite3 的技术栈是正确的选择 — 保持不变。

3 Agent 架构深度拆解（逐产品）

🔵 KinetAios — 五引擎热切 + ReAct/Plan-Execute 双模 v2.7

源码: src/main/AgentLoop.ts (670行) + DirectV2Engine.ts (1300行) + engines.ts (822行) + TaskManager.ts (1217行)

核心架构：三进程桥 + 五引擎

  • 主进程 (main): Electron 主进程, 全 Node 权限。拥有 AgentLoop / DirectV2 / DirectV3 ReAct 引擎、SQLite、IPC handlers、CLI spawn、全局热键
  • 渲染进程 (renderer): vanilla TS dashboard + Quick Panel。无 Node 权限 (contextIsolation: true), 只能通过 preload 暴露的 KinetAPI 调主进程
  • preload 桥: 唯一的进程间通道。KinetAPI 接口 (shared/types.ts) 是三端同步的契约

五种引擎:

  • direct — v1 ReAct 单轮快响应 (15K trim budget, 4K truncate)
  • directV2 — Plan-Verify-Judge 四层多步累积 (80K trim, 12K truncate, appendStepSummary)
  • directV3 — 自适应流水线 (Fast/Std/Deep 三档自动路由)
  • claudeCode — spawn claude -p --output-format stream-json, NDJSON 解析, --resume 续会话
  • codex — spawn codex exec --json, JSONL 解析

关键设计：ENGINE_POLICIES 策略包

不同引擎有完全不同的上下文需求,用一个 EngineContextPolicy 对象集中管理所有"上下文魔数":

direct: { trimBudget: 15K, truncate: 4K, appendStepSummary: false } directV2: { trimBudget: 80K, truncate: 12K, appendStepSummary: true, stepSummaryMaxChars: 800 } directV3: { trimBudget: 60K, truncate: 10K, appendStepSummary: true } claudeCode: { trimBudget: 15K, truncate: 4K } // CLI 各管自己的 context

v2 还有动态预算计算: trimBudget = modelWindow * ratio, 切模型(GLM-4.6 128K → GLM-5.2 1M)只改设置不改代码。

Memory Blocks 三层记忆

  • 结构化常驻记忆: user_profile / project_context / active_goals, 每轮注入到 context
  • 长期事实记忆: 每轮自动从对话提取, FTS5 + 向量检索 (memory_embeddings 表)
  • 会话摘要: 会话结束自动生成 episodic 摘要

优势: 多引擎热切是独有差异化; Memory Blocks 设计优于竞品的静态 CLAUDE.md; 33K 行代码做到的功能密度极高

劣势: 单进程并发上限; 无 sandbox 隔离 (靠用户 confirm); Effect 全家桶(OpenCode) 和 Rust 原生沙箱(Codex)的工程质量更高

🟠 Claude Code — 闭源 CLI Agent + MCP 生态 Anthropic

@anthropic-ai/claude-code · NDJSON 流式输出 · --resume session 持久化

核心架构

  • 单一 CLI 界面: 终端交互式 TUI, 支持 -p 非交互模式 + --output-format stream-json
  • 内置工具集: Bash, Edit, Write, Read, Glob, Grep — 六件套, 简洁克制
  • Agent Loop: Anthropic Messages API + tool_use/tool_result 循环 (闭源, 无法审查细节)
  • MCP Client: 支持 stdio + SSE 两种 transport, 可接入任意 MCP server
  • 会话管理: --resume [session_id] 续接历史会话, session 持久化在 ~/.claude/
  • 权限模型: 三档 — plan (只读), acceptEdits (文件写入), bypassPermissions (完全)

Hook 系统

Claude Code 支持 PreToolUse / PostToolUse 等 hook, 允许在工具执行前后注入自定义逻辑。这是安全管控的关键机制。

跨平台 CLI spawn 细节

KinetAios 在调用 Claude Code 时, 针对 Windows 的 .cmd shim 做了特殊处理 (CVE-2024-27980):

// .cmd/.bat 走 shell:true, .exe/unix 直接 spawn // prompt 通过 stdin 传入, argv 只传 flag (防 cmd 注入) // taskkill /PID xxx /T /F 杀进程树 (kill 只杀 cmd.exe)

优势: 工具质量极高(Edit/Read 体验最好); 权限模型清晰; MCP 生态最大; 社区资源丰富

劣势: 仅支持 Claude 模型(无多模型); 闭源无法审查 agent loop; 无长期记忆(靠 CLAUDE.md 静态文件); 无可视化 dashboard

🟢 Codex CLI — Rust 原生 + 三级沙箱 105K⭐

github.com/openai/codex · codex-rs (60+ Rust crate) · Apache 2.0

核心架构

  • Rust 核心: codex-rs/ 下 60+ crate — core, exec, tui, mcp-server, protocol, sandboxing, hooks, memories, file-watcher...
  • 多入口: codex (TUI), codex exec (CLI one-shot), codex app (桌面应用), Codex Web (云端)
  • 沙箱: 三级隔离 — read-only / workspace-write / danger-full-access
  • OS 级隔离: Linux bwrap + macOS seatbelt, 真正的进程级沙箱 (不是 confirm 弹窗)
  • 模型: OpenAI Responses API, 签 ChatGPT 账号或 API key

codex-rs 模块全景

agent-graph-store → Agent 任务图持久化 agent-identity → 多 Agent 身份管理 core → 核心 Agent Loop exec → CLI one-shot 执行 execpolicy → 命令执行策略 file-search → 文件搜索 (类似 glob) hooks → 工具执行 hook linux-sandbox → bwrap 隔离 mcp-server → MCP 服务端 memories → 记忆系统 process-hardening → 进程加固 sandboxing → 沙箱抽象层 skills → Skill 系统 tools → 内置工具集 tui → 终端 UI

与 KinetAios 的集成

KinetAios 的 CodexEngine spawn codex exec --json, 解析 JSONL 输出: codex exec --json --sandbox read-only|workspace-write|danger-full-access

优势: Rust 性能 + 安全; OS 级沙箱远超 confirm 弹窗; 开源社区活跃 (105K star); 多入口设计灵活

劣势: 仅 OpenAI 模型; 无长期记忆 (靠 AGENTS.md); 无 dashboard; TUI 交互受限; 编译复杂

🟣 OpenCode — 效应系统 + 事件溯源 666K LOC

Bun + Effect 4.0-beta + SolidJS TUI + Drizzle ORM · MIT

核心架构

  • Effect 全线: 32 个子包全部基于 Effect 函数式效应系统 — Layer/Context/Service 模式
  • Event Sourcing: V2 Session Core — 每个操作 (PromptAdmitted/Prompted/ToolCalled/ToolSettled) 都是 durable event, 写入 SQLite event log, 再 project 到 session_message 表
  • Context Source 注册表: 声明式上下文管理 — 每个 Source 声明 key/codec/load/baseline/update, 用 Schema.Codec 做值等价比较实现真 diff
  • Durable Inbox: prompt 写入 SQLite 后再执行, crash 可恢复; steer/queue 双优先级队列
  • 自研 opentui: SolidJS 信号系统 → 终端渲染, 不依赖 blessed/ink
  • SDK Contract IR: HttpApi 定义 → 编译成 IR → 自动发射 Effect/Promise 双 SDK

Context Source 与 Durable Inbox 实评

基于源码精读 (320 行 index.ts + 174 行 context-epoch.ts + 288 行 input.ts):

  • 变更检测是真 diff (Schema.toEquivalence(codec)), 不是全量重发
  • Snapshot 持久化到 session_context_epoch 表, crash 后可 reconcile
  • 为两个 String 类型 source (environment + date) 造了 320 行泛型类型擦除系统 — 过度工程
  • reconcile 状态机三路分支 (Unchanged/Updated/ReplacementResult) 对"更新 system prompt"操作过重
  • registry 的 load 并行执行无依赖编排能力
  • 单节点并发模型 (RunCoordinator 用内存 Map), 多进程无防护

优势: 架构设计最先进 (Context Source / Durable Inbox / SDK IR); crash recovery 完整; 自研 TUI

劣势: Effect 全线 beta (4.0.0-beta.83) = 维护噩梦; 666K 行 monorepo 贡献门槛极高; V1/V2 双轨迁移未完成; 实际内置 source 只有 2 个

🟢 WorkBuddy — 职场 AI 工作台 腾讯

2026-03 上线 · 桌面客户端 · Token Credits 套餐 · 适配 QQ/企微生态

  • 自然语言任务下达: "帮我做一份上周销售数据汇总PPT" → 自动拆解 → 执行 → 交付

  • 本地文件操作: 授权目录内读写, 批量处理, 成果保存到本地

记忆方案分层

🔵 KinetAios: 最丰富的记忆栈

  • Memory Blocks: user_profile / project_context / active_goals — 每轮注入, 结构化
  • FTS5 history 表: 全量对话文本索引, recall_memory 用 bigram 分词
  • memory_embeddings 表: 向量检索 (embedding model), 语义近似召回
  • memories 表: 自动提取的事实, 带权重 + 使用计数
  • memory_triples 表: 知识图谱 (subject-predicate-object)
  • episodic 摘要: 会话结束自动生成, ⭐ 评级, recall_memory 可搜
  • conv_facts 表: 会话级锚点 (remember_fact / recall_fact)

六层记忆系统, 任何竞品都没有这么深。FTS5 + 向量双通道检索是硬核优势。

🟣 OpenCode: 最"正确"的设计

  • Context Source 注册表: 声明式, 有类型, 可增量 diff — 但实际只有 2 个 source
  • Context Epoch: baseline + snapshot 持久化到 SQLite, crash 可 reconcile
  • Compaction: 上下文溢出时自动摘要压缩, 压缩后发 replacement
  • Durable Inbox: prompt → SQLite → wake → drain, steer/queue 双优先级

设计比实现更令人印象深刻 — 复杂度高但内置 source 少, 投入产出比存疑。
