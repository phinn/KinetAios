⚙️ KinetAios 四引擎架构分析

DirectEngine (v1) · DirectV2Engine (v2) · ClaudeCodeEngine · CodexEngine — 源码级深度对比

一、引擎总览

DirectEngine

Kaios (Direct)
  • 文件: engines.ts
  • 架构: 单轮 ReAct loop
  • 模型: 用户配置的 LLM provider
  • 工具: 全部内置工具 (10+)
  • 上下文: directHistory 跨轮持久化
  • 压缩: compactHistory 摘要压缩

DirectV2Engine

Kaios v2 (Plan·Verify)
  • 文件: DirectV2Engine.ts
  • 架构: Plan → Execute → Verify → Judge
  • 模型: 复用 v1 的 provider
  • 工具: 复用 v1，Planner 阶段只读
  • 重试: 每步 MAX_RETRIES=3
  • 重规划: Judge 判定未完成 → Replan (≤2 次)

ClaudeCodeEngine

Claude Code
  • 文件: engines.ts
  • 架构: 外部 CLI claude -p
  • 模型: Claude (Anthropic 自有模型)
  • 协议: NDJSON stream-json
  • Session: --resume <session_id>
  • 注入: --append-system-prompt

CodexEngine

Codex
  • 文件: engines.ts
  • 架构: 外部 CLI codex exec
  • 模型: OpenAI Codex (GPT 系列)
  • 协议: JSONL 事件流
  • Session: resume <session_id> 子命令
  • 注入: 前置拼到 prompt

DirectEngine (v1) — 单轮 ReAct

│                    DirectEngine v1                    │
│                                                       │
│  systemPrompt ──► runAgentLoop ──► 事件流 (token/tool)│
│       │              ↑    ↓                           │
│  memoryBlock         │    └── 工具调用 (shell/write…) │
│  rulesBlock     ┌────┘                                │
│  contextBlock   │ LLM ← (tool_results 循环直到无调用) │
│  skillBlock     └──────────────────────────────────── │
│                                                       │
│  结束 → compactHistory → directHistory (持久化)       │
└─────────────────────────────────────────────────────┘

DirectV2Engine (v2) — 四层架构

┌──────────────────────────────────────────────────────────────┐
│                    DirectV2Engine v2                          │
│                                                                │
│  Phase 1: Planner  (只读工具 + PLANNER_PROMPT)              │
│    │  runAgentLoop → 探查项目 → 输出 <plan> JSON               │
│    │  parsePlan() 解析 → Plan{goal, steps[]}                    │
│    │                                                           │
│    ├─ 无 plan? → 退化 v1 模式 (autoVerify + finalize) → done │
│    │                                                           │
│  Phase 2: Executor  (全工具 + STEP_EXECUTOR_PROMPT)       │
│    │  for each step:                                            │
│    │    runAgentLoop(systemPrompt, history=execHistory)         │
│    │    step.verifyCommand? → runVerify (走 confirm)            │
│    │    验证失败? → 重试 (≤3 次, 注入上次失败结果)              │
│    │                                                           │
│  Phase 3: Verifier  (全局 autoVerify)                    │
│    │  detectVerifyCommand: tsc / npm test                      │
│    │                                                           │
│  Phase 4: Judge    (独立 LLM 调用, 不信模型自述)       │
│    │  JUDGE_PROMPT → {completed: bool, reason: string}          │
│    │                                                           │
│    ├─ 未完成 & replanCount < 2? → Replan (回到 Phase 1)    │
│    └─ 完成 / 达上限 → finalizeContext → done                   │
│                                                                │
│  事件转发: forwardEvent() 拦截子 loop 的 done/error            │
│  上下文: finalizeContext → compactHistory → directHistory      │
└──────────────────────────────────────────────────────────────┘

ClaudeCodeEngine — CLI 进程流

┌──────────────────────────────────────────────────────────────┐
│                   ClaudeCodeEngine                             │
│                                                                │
│  spawn: claude -p --output-format stream-json --verbose        │
│         --include-partial-messages                             │
│         --permission-mode plan|acceptEdits|bypassPermissions   │

│         [--append-system-prompt <persona+rules+context+mem>]   │

│  stdout → 逐行解析 NDJSON:                                      │

│    tool_use   → pending map (id→name+args)                     │
│    tool_result→ onEvent(tool, name, result)                    │
│    result     → cost(total_cost_usd) + done/error              │
│                                                                │
│  无 directHistory — 上下文完全由 CLI --resume 管理              │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│                     CodexEngine                                │

五、优缺点对比

🔵 DirectEngine (v1)

优点

  • 轻量，单次 ReAct loop 响应快
  • 全功能工具链 (10+ 内置工具)
  • dispatch_agent 子 agent 派发
  • compactHistory 长对话摘要压缩
  • 支持任意 OpenAI 兼容 provider
  • 多模态图片输入
  • Anthropic prompt cache 优化

缺点

  • 无规划阶段，复杂任务容易"边想边改"
  • 无自动验证，依赖模型自觉跑 tsc/test
  • 无 Judge 裁决，模型说"完成"就完成
  • 失败不自动重试

🟣 DirectV2Engine (v2)

优点

  • Plan-first 架构，先探查再动手
  • 按步骤串行执行，每步有独立上下文
  • 自动验证 (detectVerifyCommand)
  • 失败重试 (MAX_RETRIES=3)
  • Judge 独立裁决 (不信模型自述)
  • Replan 循环 (Judge 判定未完成 → 重新规划)
  • 简单任务自动退化为 v1 模式

缺点

  • 多轮 LLM 调用 (Planner + 每步 + Judge)，token 消耗显著增加
  • 步骤串行执行，无法并行
  • 简单任务退化路径不如 v1 直接（多了一次 plan 检测开销）
  • Judge 用同一 provider，非真正的"独立第三方"

🟠 ClaudeCodeEngine

优点

  • Claude 原生工具调用能力（Anthropic 优化）
  • --resume 跨轮上下文由 CLI 管理，app 无需维护 history
  • --append-system-prompt 注入规则
  • stream-json 支持 partial messages（更细粒度的流式）
  • permission-mode 沙箱精确控制

缺点

  • 依赖外部 CLI 安装 (enableCliEngines)
  • 无 dispatch_agent 子 agent
  • 无多模态支持
  • cost 只有 $ 总额，无 token 明细
  • .cmd shim 通过 shell:true 存在命令注入风险 (已知 MVP 限制)
  • 不支持 Skill (/ 命令)

🟢 CodexEngine

优点

  • OpenAI Codex/GPT 原生能力
  • resume 子命令跨轮上下文
  • JSONL 事件流结构清晰 (item.completed / turn.completed)
  • 沙箱三档: read-only / workspace-write / danger-full-access
  • patch_applied 事件可追踪文件修改

缺点

  • 依赖外部 CLI 安装
  • 无 --append-system-prompt → 规则/记忆只能拼 prompt (打乱缓存)
  • 无 dispatch_agent
  • 无多模态支持
  • exec 级 flag 必须在 resume 之前 (clap 解析顺序限制)
  • 不支持 Skill

六、代码层面的问题与发现

🔴 严重 (影响功能正确性)

1
V2 步骤执行缺少上下文隔离

execHistory 在步骤间是累加的 (execHistory = stepMessages)，但 runAgentLoop 的 history 参数会被 trimHistoryToTokenBudget 裁剪。多步任务中早期步骤的工具结果会被裁掉，后续步骤看不到前步的完整上下文 —— 可能导致重复操作或遗漏依赖。

2
V2 未处理 skillBlock

EngineRunOpts 有 skillBlock 字段，DirectEngine (v1) 将其拼入 systemPrompt，但 DirectV2Engine.run() 的解构里完全没有 skillBlock —— 用户在 v2 引擎中使用 /skill 命令时，skill 指令会被静默丢弃。

3
V2 Replan 时 Planner 使用全工具集而非 readOnlyTools

Phase 1 的 Planner 正确使用了 readOnlyTools()，但 replan() 方法中重新规划的 runAgentLoop 调用使用了从外层传入的 tools 参数（即 allTools()），这意味着 Replan 阶段模型可以使用写工具 —— 违背了"规划阶段禁止写操作"的设计原则。

🟡 设计问题 (可改进)

4
V2 Judge 使用同一 provider，非真正独立

Judge 的设计意图是"不信模型自己说搞定了"，但 judge() 用的是同一个 provider（即同一个 LLM）。如果模型在执行阶段自我欺骗，Judge 也可能得出相同结论。真正的独立裁决需要用不同模型或至少不同 systemPrompt。

5
四引擎对多模态支持不一致

只有 Direct v1 在 runAgentLoop 内完整实现了 \x00IMAGES[...]\x00 标记 → ContentPart[] 的转换。V2 依赖 runAgentLoop 所以间接支持，但 CLI 引擎 (Claude/Codex) 完全丢弃图片输入。用户在 Claude/Codex 引擎拖入图片后无任何提示。

6
V2 parsePlan 容错不足

parsePlan() 依赖正则匹配 <plan>...</plan> 标签。如果模型输出了裸 JSON 或格式略有偏差（如 <plan json>），虽然有 fallback，但 fallback 逻辑尝试匹配 { 开头 —— 如果模型在 plan 前面有寒暄文字，fallback 也会失败，最终退化为 v1 模式（无警告）。

7
V2 验证步骤跳过逻辑可能掩盖问题

步骤验证失败 MAX_RETRIES 次后，代码发一条 status 事件 "步骤最终失败,继续下一步" 就跳过了 —— 后续步骤可能依赖前步的产出，静默继续可能导致连锁失败。更好的做法是：步骤失败 → 立即触发 Judge 或 Replan。

8
CLI 引擎的 .cmd shim 安全风险

resolveBin() 在 Windows 上检测到 .cmd/.bat 后缀时启用 shell: true。prompt 内容通过命令行参数传递，如果包含 &|>< 等 cmd 元字符，理论上存在命令注入风险。代码注释标记为 "acceptable for MVP"。

🟢 小问题 / 细节

9
V2 forwardEvent 拦截逻辑

子 runAgentLoop 每次结束都会发 done/error，v2 通过 forwardEvent 拦截这些事件（转为 status），仅在最终发一次 done。设计正确，但如果子 loop 真的出错（如 LLM 400），error 被吞为 status，用户只看到一条状态消息而不清楚是严重错误。

10
Codex flag 顺序陷阱

codex exec 的 exec 级 flag (--json -C --add-dir -s) 必须在 resume 子命令之前，否则 clap 解析器将它们视为 resume 的参数并退出 status=2。代码已处理但无注释解释原因（原文注释在源码中有）。

11
V2 退化模式的 done 事件

当 parsePlan() 返回 null（无 plan），v2 走退化路径后直接 onEvent({ type: 'done' })，但此时 plannerMessages 已经包含了一轮完整的 ReAct 交互。退化模式实际上跑了两轮（planner 的 runAgentLoop 内部），而 v1 只跑一轮 —— 性能不对等。

12
autoVerifyFromSteps 参数不一致

定义签名为 (conv, ctx, signal, onEvent, messages)（5 参数），但之前的代码中曾出现 6 参数调用 (conv, snap, ctx, signal, onEvent, ...)。当前代码看起来已修复，但 conv 参数在内层只用于 conv.cwd，可以直接传 cwd 减少耦合。

七、选型建议

📌 日常快速任务 → 用 DirectEngine (v1)。单轮 ReAct 够用，工具齐全，响应快。
📌 复杂多文件任务 → 用 DirectV2Engine (v2)。Plan-first 先规划再执行，自动验证 + Judge 裁决 + Replan 循环，更像人类工程师。但注意 token 消耗约为 v1 的 2-3 倍。
📌 需要 Claude 原生能力 → 用 ClaudeCodeEngine。适合 Claude 擅长的代码推理 / 大规模重构。前提是已安装 claude CLI。
📌 需要 OpenAI 生态 → 用 CodexEngine。适合 GPT 系列模型 / OpenAI 工具链。前提是已安装 codex CLI。
